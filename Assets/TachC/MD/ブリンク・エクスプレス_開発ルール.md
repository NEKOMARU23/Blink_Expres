# ブリンク・エクスプレス 開発ルール

最終更新：2026-11-07

この文書は、Unity版『ブリンク・エクスプレス』をプログラミングするときのルールと、Gitの使い方をまとめたもの。ゲームの仕様（操作、数値、ステージ）は「企画書」と「仕様書」に従う。この文書はコードと履歴の進め方だけを扱う。

- 企画書：「ブリンク・エクスプレス_企画書.md」
- 仕様書：「ブリンク・エクスプレス_仕様書.md」
- Webデモ版（HTML、Three.js）は手触りを確かめるための参考。コードを移植する義務はない。C#で作り直し、Unity らしい形にしてよい。
- 仕様と実装がずれたら、先に仕様書を直してからコードを直す。

- Unity 6000.6.3f1（ProjectSettings/ProjectVersion.txt）

## 設計の原則

1. **数値はコードに直接書かない。** 仕様書の「調整パラメータ一覧」にある値は、ScriptableObject（`PlayerTuning`、`BeaconTuning` など）にまとめ、インスペクターで調整する。ただし、仕様書の表にある値（敵の硬さ、コインの数、ランクの条件など）は、`EnemyRules`、`CoinRules`、`StageRank` のような静的クラスに置き、テストで確かめる。
2. **単位を守る。** 距離は m、速さは m/s、時間は秒。表示のkm/hは `m/s × 2.4` で計算する。変数名や注釈で単位が分かるようにする（例：`speedMps`、`maxSpeedMps`）。
3. **スローと実時間を分ける。** 照準中は世界が0.25倍速になるが、UI、カメラ操作、ゲージの消費は実時間で動く。`Time.timeScale` は使わない。ゲーム内時間は、ビーコンの `WorldTimeScale` を掛けて進める。
4. **速さを保つ。** ワープ、ジャンプ、壁、キノコは「速さは変えず、向きだけ変える」を基本にする。速さを変えるのは、仕様書に書かれた加速・減速の要因だけにする（コイン、粉砕、泥、障害物、天井、弾かれる）。
5. **移動は CharacterController で行い、速さは自前で管理する。** 速度は Model が X・Y・Z の成分で持ち、View は `CharacterController.Move` に渡すだけにする。落下は向きだけを曲げる。
6. **ワープ弾は線分で判定する。** 仕様書どおり 1/120 秒刻みで、直前の位置から次の位置までを Raycast で調べる。予測線と実際の飛行は、同じ刻みで計算する。
7. **状態は enum と、それを切り替える専用のメソッドで持つ。** 他のクラスから状態を直接書き換えない。
8. **純粋な計算は Model に置く。** Unity に依存せず、EditMode テストで確かめる。View は表示と入力だけにする。

## アーキテクチャ（Reactive MVP）

方式は **Passive View**（受動的なView）。View は表示と入力の通知だけを行い、判断はすべて Presenter が行う。

### 層

依存は外側から内側だけに向ける（View → Presenter → Model）。内側は外側の名前を知らない。

| 層 | 役割 | Unity への依存 |
| --- | --- | --- |
| Model | ゲームのルールと状態。純粋な C# | なし（位置や向きに `Vector3` を使う場合は、型だけ使う） |
| Presenter | Model と View をつなぐ。入力を Model に渡し、結果を IView に反映する | 最小限（`MonoBehaviour` は継承しない） |
| View | 表示と入力の通知、衝突や当たりの検出。`MonoBehaviour` | あり |

- View は「値を表示する」「入力を通知する」「衝突を検出して Model に渡せる形にする」だけにする。判定や計算は書かない。
- Presenter は、View を `IXxxView` というインターフェース越しにだけ触る。テストで差し替えられるようにするため（例：`BeaconPresenterTests` の偽の View）。
- フォルダは機能ごとに分け、中を `Model/`、`Presenter/`、`View/` に分ける（`Player`、`Beacon`）。
- 機能の中心にならない単純な型（例：`EnemyRules`）は、`Model/` に置いてよい。

### Repository（保存）

- 保存と読み込みは、Repository の窓口を通す。例：自己ベストのゴースト（`GhostStore`）。
- 保存に失敗してもゲームは止めない。警告を出して続ける。

### リアクティブ（R3）・非同期（UniTask）

- まだ使っていない。使い始めるときに、この節を書き直す。
- 使うときの方針（予定）：Model の状態は `ReactiveProperty` で公開し、Presenter が購読する。非同期は `UniTask` を使い、`async void` は使わない。キャンセルは `CancellationToken` で行う。

### 重複の削減（Template Method）

- 処理の順番が決まっていて中身だけ違うもの（例：敵の反応、仕掛けの当たり処理）は、基底クラスに骨組みを書き、差分だけを派生クラスで書く。
- 基底クラスのメソッドは `protected abstract` か `protected virtual` にし、サマリーに「派生クラスで何を書くか」を書く。
- まだ該当する箇所は少ない。同じ処理が3回目に出たときに検討する。

## パッケージの導入

- R3 と UniTask は、Unity のパッケージマネージャで入れる。導入するときは、そのバージョンを `Packages/manifest.json` と一緒にコミットする。
- **R3 の DLL は、リポジトリに入れたままにする。** 理由：Unity 用の公式のパッケージ（OpenUPM、Git の URL）は、DLL（`R3.dll`）を含んでいないため。
  - 入れている DLL：`Assets/Plugins/R3/` の `R3.dll`、`System.Threading.Channels.dll`、`Microsoft.Bcl.TimeProvider.dll`、`Microsoft.Bcl.AsyncInterfaces.dll`、`System.Runtime.CompilerServices.Unsafe.dll`
  - 取得元：NuGet の R3 1.3.1（`https://www.nuget.org/api/v2/package/R3/1.3.1`）と、その依存の NuGet パッケージ
  - ライセンス：R3 は MIT
  - R3 のバージョンを上げるときは、この節とフォルダの DLL を同時に差し替える。
- 導入後は、Unity 6000.6.3f1 で動くかを確認する。動かないバージョンは使わない。

## 名前空間とアセンブリ

- すべてのスクリプトは名前空間を付ける。ルートは `BlinkExpress`。
- 名前空間はフォルダと対応させる（例：`Scripts/Player/Model/` → `BlinkExpress.Player.Model`）。
- 使っている名前空間：`BlinkExpress.Core`、`BlinkExpress.Player.{Model,Presenter,View}`、`BlinkExpress.Beacon.{Model,Presenter,View}`、`BlinkExpress.Enemy.{Model,View}`、`BlinkExpress.Ghost.{Model,Store,View}`、`BlinkExpress.Stage.{Model,View}`、`BlinkExpress.Tuning`。
- アセンブリ（asmdef）：
  - `BlinkExpress`（`Assets/Scripts/`）：ゲーム本体
  - `BlinkExpress.Tests.EditMode`（`Assets/Tests/EditMode/`）：EditMode テスト
  - `BlinkExpress.Editor`（`Assets/Editor/`）：Editor 専用の処理（ステージの組み立てなど）。`UnityEditor` を使うのはここだけにする。

## null チェック

- `null` のとき、ゲームが止まる、または表示が壊れる場合は、必ずチェックする（例：`Tuning` が未設定、カメラが無い）。
- `null` でも動いてしまう場合は、チェックを入れない（例：ゴーストの表示。無くてもゲームは動く）。
- 判断に迷ったら、`null` になったときに何が起きるかを確かめてから決める。
- 必須の参照は `Awake` で取得し、取れなければ `Debug.LogError` を出して `enabled = false` にする。

## シングルトン

- シングルトンが必要なときは、基底クラス `Singleton<T>`（`BlinkExpress.Core`）を継承する。
- 直接 `static` の `Instance` を手書きしない。
- `Awake` を書くときは、`base.Awake()` を先に呼ぶ（2つ目のインスタンスを破棄するため）。
- シングルトンは「ゲーム全体で1つだけ」のものに限る（例：`StageProgress`）。
- 1つのステージでしか使わないものは、シングルトンにせず、シーンの中で参照する。

## イベント

- **複数の場所で使うイベント**は `EventBus`（静的クラス）に載せる。送る側と受ける側が互いを知らなくてよくする。例：「敵を粉砕した」「コインを取った」。まだ作っていない。必要になったら作る。
- **1か所だけで使うイベント**は、C# の標準の `event` や `Action` を使う。バスに載せない。
- イベントの名前は過去形で書く（例：`EnemySmashed`、`BeaconWarped`）。
- 購読したら、必ず `OnDisable` か `OnDestroy` で解除する。

## コメントとサマリー

- コメントは日本語で書く。
- クラスには必ず `/// <summary>` を付ける。何の責務を持つかを書く。
- 公開メソッド、公開プロパティには必ず `/// <summary>` を付ける。
- 名前だけでは誤解しそうなものには、サマリーで単位や意味を書く。例：`SpeedMps` は m/s、`YawRad` は rad。
- 非公開の処理は、「なぜそうするか」が分かりにくいときだけコメントを書く。
- 仕様書の数値や判定の根拠は、該当する箇所に仕様書の節名を入れる（例：`// 仕様書「チェイン」の節`）。

## 処理の書き方

- 毎フレームの処理（`Update`）の中で `GetComponent`、`FindObjectOfType`、`Find` を呼ばない。起動時に取得してキャッシュする。ただし、衝突の検出（`Physics.OverlapSphere`、`RaycastAll`）は毎フレーム行ってよい。その場合は、件数が増えたときに見直す。
- パーティクル、コインの取得演出、ビーコンの見た目は、オブジェクトプールを使う（まだ作っていない）。
- 外部のアセットやパッケージを追加するときは、先に理由を書いて確認する。

## テスト

- 純粋な計算（Model）は EditMode テストを書く。仕様書の数値が変わったら、対応するテストも直す。
- PRを出す前に、EditMode テストが全部通ることを確認する。
- テストの実行：
  - まず、CLI（`unity command test run --mode EditMode`）で実行する。
  - CLI が時間切れになったり、Editor が応答しなくなったりしたら、Unity の Test Runner（Window > General > Test Runner > EditMode > Run All）で実行する。
- テストの前に、Unity でシーンを保存しておく（下の「Unityのシーンとアセット」を参照）。

## Unityのシーンとアセット

- シーンは1ステージ1つ。仕掛けや敵は Prefab にして、シーンには配置だけを置く（まだ Prefab は作っていない。今は Editor の組み立て処理で配置している）。
- 「Scene(s) Have Been Modified」のダイアログでは、**Save** を選ぶ。**Don't Save** を選ぶと、配線（参照）が消える。
- 保存ダイアログが出ている間は、Unity が CLI の命令を受け付けない。CLI が応答しないときは、まずダイアログを確認する。
- 共有している Prefab や ScriptableObject を変えるときは、コミットメッセージに影響範囲を書く。
- 同じ `.unity` ファイルを複数人が同時に編集しない。
- 大きな音声、画像、動画は、Git LFS の対象かを `.gitattributes` で確かめてから追加する。

## Git

### ブランチ

- `main` は動く状態を保つ。作業は機能ごとのブランチで行う。
- ブランチ名は `接頭語/kono/実装内容`。実装内容は英語のケバブケースで書く。
  - 例：`feat/kono/player-movement`、`feat/kono/jump-air`、`fix/kono/wall-climb-height`
- 接頭語は次の表のものを使う。
- 機能どうしが前の機能の上に乗るときは、前の機能のブランチから続けて作る（積み上げ）。
- `main` への force push はしない。**強制 push は、どのブランチでも行わない。**
- push は、依頼されたときか、ブランチの作業が区切れたときだけにする。

### 接頭語

| 接頭語 | 使う場面 |
| --- | --- |
| feat | 機能を追加した |
| fix | 不具合を直した |
| tune | 数値（ScriptableObject）を調整した。本文に変更前と変更後、理由を書く |
| refactor | 動作を変えずにコードを整理した |
| test | テストを追加、修正した |
| docs | ドキュメント（企画書、仕様書、この文書）を変えた |
| chore | 設定、ignore、パッケージなど、その他 |

### コミット

- **要素ごとに1コミットに分ける（細かく分ける）。** 1コミットには、1つの要素（機能の1つ分）だけを入れる。
  - 例：「泥・跳ねるキノコ・グラインドレール・障害物・天井の仕掛けを追加」は、次のように5コミットに分ける。
    1. `feat:泥（減速床）を追加`
    2. `feat:跳ねるキノコを追加`
    3. `feat:グラインドレールを追加`
    4. `feat:登れない障害物（紫の壁・倒木）の減速を追加`
    5. `feat:天井に当たったときの減速を追加`
  - 共通の土台（基底クラスや、後の要素が使う型）は、使う要素より先に、別のコミットにする（例：`feat:シングルトンの基底クラス Singleton<T> を追加`）。
  - 機能の追加とリファクタリングは、必ず別のコミットにする。
  - 例外：2つの要素が互いを参照していてコンパイルできない場合は、1コミットにまとめてよい。その場合は本文に理由を書く。
  - 各コミットは、できる限りコンパイルできる状態にする。コンパイルできない中間のコミットは、本文にその旨を書く。
- 形式：`接頭語:内容`（内容は日本語。コロンのあとに空白を入れない）
- 件名は50文字以内を目安にする。
- 本文には、理由、仕様書の該当節、テストの結果を書いてよい。
- Claude Code が作成したコミットには、Co-Authored-By の行を付ける（作業時点の指示に従う）。

例：

```
feat:ワープ弾の線分判定を追加

1/120秒刻みで前の位置から次の位置までをRaycastで調べる。
仕様書「ビーコンの弾道」の節に合わせた。
```

### プルリクエスト（PR）

- タイトルは、何をしたかが一目で分かる日本語にする（例：「プレイヤーのワープと向きの変化を実装」）。
- ベースは、積み上げの場合は前の機能のブランチにする。前の PR がマージされたら、ベースを `main` に変える。
- 説明には次を書く。
  - 概要：何のための変更か。積み上げの場合は、どのブランチの上に積んだかを書く
  - 変更内容：主な変更点を箇条書き
  - 関連する仕様書の節
  - 確認方法：どうテストしたか（EditMode テストの結果、プレイした内容）
  - 残っている課題や、確認してほしい点
- Claude Code が作成したPRの説明の最後には、次の行を付ける。
  `🤖 Generated with [Claude Code](https://claude.com/claude-code)`
- **PR のマージは、人が行う。** Claude Code はマージしない。

### Unity特有の扱い

- `.meta` ファイルは、対応するアセットと必ず一緒にコミットする。`.meta` だけを残したり、アセットだけをコミットしたりしない。
- 次は `.gitignore` で除外済みなので、コミットしない：`Library/`、`Temp/`、`Logs/`、`UserSettings/`、`Obj/`、`Build/`、`*.csproj`、`*.sln`、`*.slnx`
- `ProjectSettings/` の変更は、意図した設定変更のときだけコミットする。Unityが自動で書き換えた差分は、内容を見て戻すか判断する。

### コミット前の確認

1. `git status` で、関係のないファイルが混ざっていないか確かめる。
2. `git diff --stat` で、変更の量が想定どおりか確かめる。
3. 差分に `Library/` や大きなバイナリが混ざっていないか確かめる（R3 の DLL のように、意図して入れるものは除く）。
4. テストが通っていることを確認する。

## 進め方

1. 仕様書の該当する節を読んでから作業する。
2. 小さな単位で実装し、動くところまで確かめてからコミットする。機能ごとにコミットを分ける。
3. 数値の調整は、コードの変更と分けてコミットする（`tune:`）。
4. 手触りの判断は実際にプレイして行い、結果を仕様書の「試作で変えたこと」の表に残す。
5. 見た目は後で決める。まずは機能を作り、見た目は仮のまま進める。
